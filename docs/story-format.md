# The Story format (`nitewatch.story/v1`) and the Keystone export

A **Story** is NiteWatch's answer to "why did this connection happen?": the
causal chain behind one connection, taken from the GoRapide poset at the moment
the connection was recorded, and stored with it in the ledger. It is frozen when
written. The account of an event never changes afterwards, even when the live
causal window has long since rolled over.

This document is the contract for anything that reads a Story from outside the
agent. Today that means Keystone, the portfolio's correlation tier, through the
export described below.

## Shape

```json
{
  "schema": "nitewatch.story/v1",
  "steps": [
    {"kind": "ProcStart",  "source": "winword.exe",    "detail": "pid 100",          "lamport": 1, "pid": 100, "image": "C:\\Program Files\\Office\\winword.exe"},
    {"kind": "ProcStart",  "source": "powershell.exe", "detail": "pid 220",          "lamport": 2, "pid": 220, "image": "C:\\Windows\\powershell.exe"},
    {"kind": "DNSQuery",   "source": "",               "detail": "evil.example",     "lamport": 3, "pid": 220},
    {"kind": "NetConnect", "source": "",               "detail": "198.51.100.7:443", "lamport": 4, "pid": 220}
  ],
  "edges": [{"from": 0, "to": 1}, {"from": 1, "to": 2}, {"from": 1, "to": 3}, {"from": 2, "to": 3}],
  "mermaid": "flowchart TD\n  n0[...]\n  n0 --> n1\n ...",
  "narrative": "powershell.exe was started by winword.exe. It looked up evil.example, connected to evil.example (198.51.100.7:443).",
  "context": { "...": "what else the program was doing; informational" }
}
```

| Field | Meaning |
|---|---|
| `schema` | `"nitewatch.story/v1"`. **Absent on Stories recorded before 0.1.8-pre** — see *Older stories*. |
| `steps` | Every event in the chain, in **Lamport (happens-before) order**. The last step is always the event the Story explains (today, a `NetConnect`), and every other step is one of its causal ancestors. |
| `steps[].kind` | `ProcStart`, `ProcExit`, `DNSQuery`, `NetConnect`, `FileWrite`, … — the agent's event kinds. |
| `steps[].source` | Display name of the process image (`powershell.exe`). Empty when the event did not carry its own image. |
| `steps[].detail` | The interesting parameter, for display: `pid N`, a query name, `ip:port`, a path. |
| `steps[].lamport` | The poset's Lamport clock. Orders events; **does not by itself mean one caused the next.** |
| `steps[].pid`, `steps[].image` | The process the event belongs to: numeric PID and full image path. Absent when unknown. |
| `edges` | The poset's **direct causal edges** between steps, as indices into `steps`: `steps[from]` caused `steps[to]`. This is the graph. |
| `mermaid` | The same graph drawn as a Mermaid flowchart (arrows are `edges`). Presentation only. |
| `narrative` | The chain as one paragraph of plain English, written once at record time. Templated, never generated by a model. |
| `context` | Other activity of the same program near the time. Informational; not part of the causal claim. |

## Rules for consumers

1. **Causation is `edges`, never step order.** Two adjacent steps are often
   unrelated: when a different program resolved the name that was dialed, that
   program's whole lineage sits in the chain, sorted in among the dialer's own
   ancestors. Reading "the previous `ProcStart` is the parent" names the wrong
   program. NiteWatch has twice shipped a fix for exactly that class of false
   attribution (recycled PIDs, recycled file handles); a consumer must not
   reintroduce it.
2. **A process's parent** is the `ProcStart` step with an edge *into* that
   process's own `ProcStart`. If there is no such edge, the parent was not
   observed (it started before the agent did), and the answer is "unknown".
3. **Within one host only.** Every edge is a causal relation the agent observed
   on its own machine. A Story never asserts causality across machines.
4. **Unknown fields are ignored**, so v1 can gain optional fields without a
   version change. Removing or redefining a field is a new schema version.

### Older stories

Stories written by 0.1.7-pre and earlier have `steps`, `mermaid`, `narrative`
and `context`, but no `schema`, no `edges`, and no `pid`/`image` on steps. Their
`mermaid` joins the steps in Lamport order, so its arrows are **not** causal
edges. Treat such a Story as an ordered list of related events with no parent
information, which is exactly how the export below treats it.

## The Keystone export

```bash
nitewatch -db nitewatch.db -export-keystone export.json
```

One-shot: it reads the ledger, writes the file (owner-only permissions; it names
every program and destination, with full paths), and exits. It starts no sensor
and contacts nothing. **NiteWatch never sends this anywhere itself.** Carrying
the file to a Keystone deployment is the user's act.

`-export-host` overrides the host name stamped on records (default: this
machine's name); `-export-limit` caps the number of most-recent ledger rows read
(default 10000).

```json
{
  "schema": "nitewatch.keystone-export/v1",
  "generated_at": "2026-10-25T12:00:00Z",
  "agent": "0.1.8-pre (abc1234)",
  "src_host": "WKSTN-07",
  "flows":   [{"src_host": "WKSTN-07", "dst": "evil.example", "port": 443}],
  "events":  [{"src_host": "WKSTN-07", "pid": 220, "image": "C:\\Windows\\powershell.exe",
               "user_sid": null, "parent_pid": 100, "parent_image": "C:\\Program Files\\Office\\winword.exe",
               "dst": "evil.example"}],
  "stories": [{"connection_id": 7, "src_host": "WKSTN-07", "dst": "evil.example", "port": 443,
               "story": { "schema": "nitewatch.story/v1", "...": "..." }}]
}
```

Each section is in the shape one of Keystone's parsers reads, so the one file
feeds all of them:

| Section | Keystone parser | Observation kind |
|---|---|---|
| `flows` | `parse_nitewatch_egress` | `net.egress` |
| `events` | `parse_nitewatch_causal` | `nitewatch.causal` (ADR-0029) |
| `stories` | — (no Keystone reader yet) | the explanation contract (ADR-0006) |

Details a consumer should know:

- **Egress only.** Inbound connections are left out of every section.
- `dst` is the domain the program looked up when there was one, else the address.
- `flows` and `events` are de-duplicated (one per destination+port, one per
  process+destination); `stories` keep one per ledger row.
- `parent_pid`/`parent_image` come from Story edges and are `null` when the spawn
  was not observed or the Story predates edges. They are never inferred.
- `user_sid` is always `null`: the agent does not collect user SIDs today.

### Contract test

Keystone is a private repository, so the check that the export still parses is a
script rather than part of `go test`. It copies Keystone's connector into a
temporary package (never touching the Keystone checkout) and runs it on a real
export:

```bash
cd agent
nitewatch -replay testdata/traces/malicious.jsonl -serve=false -no-feeds -no-recon -no-resolve -db /tmp/nw.db
nitewatch -db /tmp/nw.db -export-keystone /tmp/export.json
python3 scripts/keystone-contract.py /tmp/export.json ~/Projects/keystone
```

It fails when Keystone's parser drops any flow or event, or reads a field back
differently from what was exported. Those parsers skip what they cannot read
rather than raising, so a renamed field on either side would otherwise show up
only as missing data.
