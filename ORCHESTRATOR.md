### How should Keystone receive NiteWatch data, and should Keystone adopt NiteWatch's "Story" format as its own explanation format?

- **Status:** open · **Added:** 2026-10-25 · **Reversible:** easily
- **Blocked:** nothing in NiteWatch. Decides the Keystone-side follow-up work.

**Background.** Issue #7 (shipped 2026-10-25, PR #9) asked NiteWatch to export its per-machine cause-and-effect chains for Keystone and to standardise its "Story" — the explanation stored with each connection — as a format both products share. NiteWatch's side is done: a versioned Story (`nitewatch.story/v1`, documented in `docs/story-format.md`) that now records which event actually caused which, and an export command that writes a file Keystone's existing NiteWatch readers parse without change (verified by running Keystone's own code on it). Two things are Keystone's to decide. (1) **Delivery.** NiteWatch writes a file; it never sends anything itself, because "nothing leaves the machine on its own" is the product's central promise. Keystone's NiteWatch readers are parsers, and the one Keystone already wires to a live source fetches from a URL. Keystone does have a general endpoint for submitting observations (`POST /v1/observations`), so a small converter — or a Keystone-side "import this export" command — could carry the file in; neither exists yet. (2) **The shared format.** Keystone's ADR-0006 says it will emit the same Story shape for its own explanations, but nothing in Keystone implements it yet, and nothing reads the `stories` section of the export.

**Options**

| Option | Pros | Cons | Effort |
|---|---|---|---|
| File only: a small importer (Keystone command, or a script that runs the export through Keystone's readers and posts to `/v1/observations`); Keystone adopts `nitewatch.story/v1` as written | Keeps NiteWatch's privacy promise intact; format already exists and is tested | Manual step for each machine; fine for an assessment, poor for continuous monitoring | days, Keystone side |
| NiteWatch serves an opt-in, token-protected feed on the local network | Continuous; matches Keystone's fetch model | Breaks the "nothing leaves on its own" promise for anyone who turns it on; a listening port on a consumer PC | days, plus a privacy-page rewrite |
| Defer until Keystone needs live NiteWatch data | No work | Keystone's NiteWatch views keep running on sample data | none |

**Recommendation.** File only, and have Keystone adopt `nitewatch.story/v1` as written (it can add optional fields without a version change). It fits engagement-style use — collect a machine's export during an assessment — which is how engagement-kit would use it, and it costs NiteWatch nothing it promised.

### Issue #8 asks NiteWatch to observe credential abuse (NTLM on the wire, LSASS access, pass-the-hash, lateral logons) and feed it to Keystone. Is that NiteWatch's job?

- **Resolved 2026-10-25** by Kevin
- **Decision:** Narrow #8 to an LSASS-access detection in NiteWatch, built and verified on the Windows VM; move the multi-host signals out.
- **Why:** Kevin chose the recommended option. #8 was retitled and rewritten the same day ("Detect LSASS access by non-system processes (credential dumping) → Keystone"), original text kept at the bottom; reuse across hosts, lateral auth and enterprise NTLM went to GrimthornRedbeard/keystone#20 for a future business-network sensor. #8 now waits only on the Windows VM.

**Background.** You filed #8 on 2026-09-19 from Keystone's architecture. Keystone (the correlation tier) already has a reader waiting for this data: a feed of `reuse_events`, each saying "this credential was reused from host A against host B". Four kinds of evidence are asked for. They split cleanly by what one consumer PC can actually see. **LSASS access** — a program opening the Windows process that holds logged-in users' credentials, the classic credential-dumping step — is visible on a single machine through a userland Windows event source (no kernel driver, so it fits NiteWatch's rules), and would be a genuinely useful consumer detection in its own right. **NTLM authentication** is also visible locally, but on a home PC with no domain it is mostly noise. **Hash/token reuse across hosts** and **lateral logons** are by definition about several machines in one organisation: a single home PC cannot see them, and they presume a Windows domain that consumers do not have. Separately, NiteWatch's hard rule is that nothing leaves the machine on its own, while Keystone expects to fetch a feed. Checkride, which shares NiteWatch's engine, is the enterprise Windows product, but its scope is hardening, not detection.
