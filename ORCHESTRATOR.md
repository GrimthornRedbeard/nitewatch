> 🔵 **2026-07-29 (nitewatch — overnight soak found the OTHER half of the attribution bug; 0.1.1-pre and 0.1.2-pre published).** Kevin ran the agent overnight and woke to five critical alerts — a game launcher, a WebView host, an Electron app and a browser, all "reading your Discord session tokens" within a minute. **Root cause: recycled ETW file handles.** Kernel-File names a file once on Create and then identifies it by a FileKey/FileObject on every later read; that identifier is a kernel pointer, reused the moment the file closes. The name cache made it worse twice over — `put()` returned early when the key already existed, discarding the Create that announced the handle now referred to a different file, and nothing invalidated on Close/Cleanup. **The damage was selective, not random:** only paths worth alerting on are cached (the caller filters to user-profile files first), so the cache holds little but credential stores, and every collision resolved to something alarming. Discord's leveldb churns constantly, so its paths kept winning. **The tell was the "other" context lines, not the Discord ones:** Battle.net's agent reading Zoom's webview cache and Office rule files, brave.exe writing into Claude's leveldb — correct PIDs against wrong filenames. Fixed by rebinding on put, forgetting on close, and dropping a cached name when a key is seen naming an untracked path. **The cache moved to `internal/source/namecache.go` with no build tag** — it had lived inside the Windows-only ETW file, so it could not be exercised on any machine this project is developed on, which is most of why it survived; 5 tests now cover it and 3 fail against the old logic. **This is the second half of the attribution work — the 2026-07-28 PID-occupancy fix was real and necessary but was NOT the whole cause of "one event, several programs".** Also shipped: **sorting by Sent/Received compared byte counts as text** (flat list fell through to a String() default; the grouped view, which is the default, ignored the chosen column entirely while still drawing a sort arrow), and **`#build` never landed on the download section** — the browser resolves a hash once mid-layout, six unreserved screenshots pushed the target 2,600px, and web fonts reflowed it another 30px after `load`; fixed with intrinsic image dimensions, dropping a `width:auto` that defeated them, and a post-load correction that yields if the reader has already scrolled. **Releases:** `v0.1.1-pre` (1af6af5) then `v0.1.2-pre` (12677f9), each with its own tag and published SHA-256 rather than re-pointing a version — live SHA `9504f43f…`, verified byte-for-byte against the served file and the page. **Process lesson recorded in the README:** every build this session went to a scratchpad while Kevin was picking up `dist/`, so he soaked a 13:11 build (260bc24) that predated both attribution fixes; `dist/` is the documented pickup point and must be rebuilt, `-trimpath` added so a local build can match a published hash, and the file timestamp does not identify a build (Go stamps the COMMIT time). **Soak restarted on 0.1.2-pre 2026-07-29 — the first run on code where both attribution layers are fixed, so the first false-positive number that means anything.**

> 🔵 **2026-07-27→28 (nitewatch — Kevin-directed session, NOT a rotation; work is on an UNMERGED branch — see ⚠️ below).** Long interactive session driven by Kevin's hands-on use of the agent. **Shipped (25 commits on `fix/beacon-fp-and-db-lock`):** (1) **PID-occupancy attribution rewrite** — the graph kept one `procNode[pid]` pointer meaning "whoever holds that number NOW", so late-arriving ETW events were attributed to the current occupant; a live machine produced "brave.exe wrote files in AppData\\Roaming\\Claude" and the mirror-image claim in the same minute.
